Module 4 · Pipeline and governance

Which AI apps teams need, and what has to be true before each one ships

Every app goes through the same path: intake, build, automated gates, human review, staging, release and monitoring. The data an app can touch decides how strict its gates are. Some apps are not approved at all, and this page says so.

The path to production

Seven stages, three of them human

Automated checks catch mistakes that repeat. People catch the rest, so review is the point of the pipeline, not a formality at the end.

  1. IntakeThe builder answers the intake questions. The request is matched to an existing app or sent for a new one. Data class is set here.
  2. BuildThe app is built from a scaffold with the standard guardrails already wired in: scope limits, output schema and logging.
  3. Automated gatesTests, secrets scan, static analysis, and a scope check that compares what the app can reach with what it declared.
  4. Adversarial testsThe app is run against prompt-injection and jailbreak cases. Any case that gets through blocks release until fixed.
  5. Human reviewA reviewer checks correctness, authorization, data handling and whether the app should exist. Guest-facing apps need a second reviewer.
  6. StagingThe app runs against recorded or synthetic data for at least one full week, with the output logged for review.
  7. Release and monitorReleased with an owner and a review date. Acceptance rate and complaints are tracked, and a drop triggers review.

Release gate

Check an app before it ships

Pick an app to see which checks it needs. The decision updates as you tick each one.

    Decision

    When something goes wrong

    A guest message is wrong

    Assume it will happen once. The question is how fast it is found and fixed.

    In the first hour

    • 1Pause the app for that audience. Any other audience keeps running.
    • 2Find every message sent in the window, from the log, not from memory.
    • 3Tell the guest services lead who owns the guest reply.

    In the first day

    • 4Write what went wrong, what was sent and to whom, in plain language.
    • 5Add the case to the adversarial suite so the test fails before any fix.
    • 6Review in a blameless session with the owner and a reviewer.
